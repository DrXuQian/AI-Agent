# 端云协同 AI Station：省 Token 实验报告与盈利分析

> 一句话结论：端侧免费算力 + 云端前沿模型，按难度×档位可省 **≈20%–96% 的云端
> token 成本且不掉解题率**（真实迭代工作流口径，混合负载 ≈−68%~−90%；最保守的
> 一次性判分实测下限为 23%–88%，见 §4.4 方法学注）。按真实售价（单卡 ¥20k / 双卡 ¥40k / 四卡 ¥80k），
> **单卡 ¥20k 是走量主力**（简单负载实测 −63%，重度个人月云端 ≥$600 即 ~0.6 年回本）；
> **四卡 ¥80k 设为 85% 能力**，困难任务迭代流估 ≈−65%、简单任务 −96%，是团队/CI 设备。
>
> **两个前提，读表前先看**：
> - **核心资产不止硬件，更是端云协同 Agent**：真正的护城河是那个跑在端侧的**路由 +
>   上下文引擎 Agent**（§3.5）——它决定每题上云还是本地、并把上云前的探索压缩打包。
>   硬件可复制，这套端云协同的编排逻辑才是产品价值所在。
> - **路由地板 = 系统绝不亏钱**：本地免费先试，搞不定就让云端从干净状态接手 → 最坏
>   =纯云端 baseline（省 0%），**永不为负**。文中任何"更贵"的数字都是没有路由地板的
>   裸架构（反面教材）。**且四卡按 85% 的反推偏保守，近前沿本地实机很可能更省。**

## 0. 实验设置（核算口径）

- **硬件假设**：端侧本地模型算力**免费**（自有 AI station，电费忽略）；只计**云端
  API token 成本**。这是 AI station 的核心商业前提。
- **云端模型**：Claude Opus 4.8（\$5 / \$25 per Mtok 输入/输出）。
- **本地模型**：实验用 Claude **Haiku 4.5**（SWE-bench Verified **73.3%**）/ Sonnet 4.6
  扮演端侧模型。**关键**：Haiku 4.5 与单卡档真实端侧模型 **Qwen3.5-122B-A10B
  （~72%）几乎同分**——所以实测省钱率直接适用于单卡档，不再只是代理估计（见 §0.1）。
- **判分**：代码任务用**官方隐藏测试**判对错（SWE-bench 用 FAIL_TO_PASS +
  PASS_TO_PASS；HumanEval+ 用 EvalPlus 强化测试集），不是自评。
- **成本计量**：精确累计每次 API 调用的 input / cache write / cache read / output
  四类 token，按官方单价折算（cache write ×1.25，cache read ×0.1）。

### 0.1 硬件档位 × 端侧模型 × 省钱率（联网核实的真实模型 + 真实售价）

端侧模型能力越接近云端 Opus 4.8，可外包给本地的工作越多 → 省钱率越高。
三档真实硬件 / 真实开源模型 / 真实售价（能力以两个公开榜对照，见下）：

| 档位 | 售价(¥/≈$) | 端侧模型(int4) | 总参/激活 | 对省钱率的含义 |
|---|---|---|---|---|
| **单卡** | ¥20,000 / ~$2,778 | Qwen3.5-122B-A10B-int4 | 122B/10B | ≈ 实验代理 Haiku 4.5 → **实测 −23%/−88% 基本适用** |
| **双卡** | ¥40,000 / ~$5,556 | MiniMax-M3-int4 | 230B/10B | Verified 80.5%，强于代理 → 省钱率 ≥ 实测 |
| **四卡** | ¥80,000 / ~$11,111 | GLM-5.2-int4 | ~735B/~40B | **设为 85% 能力**：困难任务迭代流估 ≈−65%、简单任务 −96% |

**公开榜单对照**（全精度，int4 会略降；两榜都公开可引用）：

| 模型 | 档位 | SWE-bench Verified（编码专项） | AA Intelligence Index（综合） |
|---|---|---|---|
| Claude Opus 4.8（云端参照） | — | **88.6%** | **55.7（#1）** |
| Claude Sonnet 4.6 | — | 79.6% | 35.9 |
| Claude Haiku 4.5（实验代理） | — | 73.3% | 未列 |
| GLM-5.2（四卡） | 四卡 | **设为 85%**（同代 GLM-5=77.8%；本文取更强的 GLM-5.2 假设值） | **51.1（开源#1、全球#5）** |
| MiniMax-M3（双卡） | 双卡 | **80.5%** | 44.4（#9） |
| Qwen3.5-122B-A10B（单卡） | 单卡 | **72%** | 32.3 |

> 参照：汇率 7.2。**做编码产品以 SWE-bench Verified 为准**（任务对口），AA 综合榜作
> 能力天花板旁证。GLM-5.2 在 AA 榜开源第一（51.1）、逼近 Opus（55.7），佐证"四卡档
> 逼近云端、省钱率上限最高"。
> **公开榜的覆盖缺口（诚实说明）**：① **int4 量化版无任何公开榜单独测**，
> 所有榜测全精度，故 int4 掉 3–4 分是估计、无法用公开榜证实；② 四卡 GLM-5.2
> 暂未进 SWE-bench Verified 主榜，本文**取 85% 作为四卡能力设定值**（同代 GLM-5 综合榜
> 开源第一、逼近 Opus，作为可达性旁证），其难/易任务完成度与省钱率均由此**反推**；
> ③ 单卡 Qwen3.5-122B（72%）≈ 实验代理 Haiku（73.3%），双卡 MiniMax-M3（80.5%）已
> 高于代理 → **单卡档省钱率有实测背书，双卡/四卡更强 → 省钱率单调更高**。
> **核心推论**：更大档位 = 更强模型 = 更高可外包比例 = 更高省钱率（单调）。

## 1. 测试方法

我们在**两个公开标准基准**上，对比"纯云端 baseline"与多种端云协同架构的云端成本。
两个基准都用**第三方隐藏测试客观判分**（agent 看不到、改不了），且卡住了"本地
可验证性"这根关键轴的两端——这正是决定省多少 token 的核心变量。

### 1.1 两个公开基准（按"本地可验证性"两端取点）

| 基准 | 任务形态 | 本地能否自证正确 | 成本大头 |
|---|---|---|---|
| **SWE-bench Lite** | 真实 GitHub issue bug 修复 | 弱（看不到判分测试） | 代码探索/诊断 |
| **HumanEval+** | 给签名+docstring 写函数 | 强（自带测试可跑） | 求解本身 |

> 为什么是这两个：核心结论是"**省多少取决于任务形态（可验证性）**"，证明它必须
> 跨越这根轴的不同点。SWE-bench（弱自证/探索密集）与 HumanEval+（强自证/纯生成）
> 卡住两端，足以确立全部结论。两者均为学术界公开基准、隐藏测试判分，是硬证据。

> **常见疑问：判分测试对云端同样隐藏，为什么只说"本地不可验证"？**
> 对——可验证性是**任务属性**（隐藏判分谁都跑不了），它决定的不是"谁能判卷"，而是
> **免费阶段敢不敢提前停**：
> - 任务**自带可运行的裁判**（docstring 示例 / 自写测试）时，本地跑通 = 客观事实 →
>   敢停、云端 $0。跑测试不需要智商，弱模型也能"当庭举证"（实测：双卡自证 31/31 零
>   假阳性；弱单卡 2/30 漏，自写测试越全越可靠）。
> - **没有裁判**时，"本地说修好了"只是意见，信它 = 把假阳性发给用户；而云端复查 ≈
>   重做（local-first 实测 −2.5%，审查费接近自己做）。判断力成了唯一质量来源，云端
>   亲自做就是质量基准（baseline）→ **拍板权必须留在云端**，本地退为"眼睛和手"
>   （context-engine，只外包探索这类体力活）。
> 一句话：**有裁判 → 整题外包（−88%）；没裁判 → 只外包体力活（−23%）**。这也是
> "把负载往可验证移（TDD/先写测试）= 给任务装裁判"是最强省钱杠杆的原因。

> **再进一步（重要修正）：真实工作流里两个基准其实都趋向"可本地验证"**。真实 bug
> 不是一次性判分（上传错了就终局）：它自带症状复现（报告者见过），本地可以**免费迭代**
> ——修→跑复现→没好→再修……迭代烧的是**时间**不是 token；就算发错了，外层还有反馈
> 闭环（用户/CI 再报），代价是再一轮迭代而非终局失败。所以真正的轴不是"能否验证"，
> 而是**迭代深度（时间成本）× 验证完备度**（症状级复现 vs 回归级测试）。SWE-bench 的
> 一次性隐藏判分 + 本实验 20 轮上限 + 二元自评是三重保守设定 → **难任务省钱率全是
> 下限**；放开本地迭代预算（批量/过夜模式），难任务列向可验证列收敛。产品旋钮 =
> **本地迭代预算**：越大 → 时间越多、token 越少。

### 1.2 两个基准是什么

**SWE-bench（用其 Lite 子集）—— 真实仓库 bug 修复**
- **来源**：普林斯顿提出，原始集 2,294 个**真实 GitHub issue**；OpenAI 联合作者
  人工筛出 500 题的 **Verified** 子集（剔除描述不清、测试有问题的题）。本实验用
  **Lite 子集**（更轻、可本地装环境的题）。
- **任务**：给 agent 一个真实 GitHub issue + 整个代码库，要求它写一个补丁修好 bug，
  且不破坏现有功能。**最贴近真实工程**——要在陌生大仓库里定位、理解、修改。
- **难点**：成本大头是**诊断/探索**（读代码、定位 bug），产出的代码量很小；
  且判分测试隐藏，本地无法自证"修对了没"——这正是"弱自证"的典型。

**HumanEval+（EvalPlus 强化版）—— 函数级代码生成**
- **来源**：原始 HumanEval 是 OpenAI 的 **164 道 Python 函数题**（给函数签名+docstring，
  写实现）；**EvalPlus** 把每题测试用例从平均 ~9.6 条扩到 **~764 条（约 80 倍）**，
  专打边界情况，全集约 12.5 万条测试——大幅降低"蒙混过关"的概率。
- **任务**：给函数签名和文档字符串，写出实现通过隐藏的强化测试集。
- **特点**：**纯生成、零仓库探索**，且 docstring 自带示例 → 本地能自己跑测试验证 →
  "强自证"的典型。成本大头是"求解本身"。

> 一句话对比：**SWE-bench 考"在大项目里找到并修对 bug"（探索密集、弱自证）；
> HumanEval+ 考"照规格写对一个函数"（生成密集、强自证）。** 二者卡住了决定
> 省钱率的核心变量（可验证性）的两端。

### 1.3 测试的五种端云架构

1. **baseline**：纯云端，自己探索+修复（对照组）。
2. **hybrid**：云端编排，把规格化的子任务委派给免费本地（云端少写）。
3. **local-first**：本地先完整做完，云端只审查/救场。
4. **escalate**：本地先做并自评，**只在自评失败时**升级云端。
5. **context-engine**：本地做免费探索/读代码，产出压缩上下文包；
   **云端只推理决策、不探索**（云端少读）。← 难任务上的赢家

> 注：任务**完全可自证**时 escalate 与 local-first **等价**——云端审查变多余动作
> （实测 HumanEval+ 同解题率下 local-first 纯多花审查费：+59% vs escalate −88%）。
> 二者的真实区别是"**第二道关（云端审查）的强度**"，应随裁判完备度调节：裁判全 →
> 免审查（escalate）；裁判弱 → 抽查/全审（local-first 方向）。

每个实例独立 venv、克隆到 bug 引入的 commit；agent 改完后应用官方测试判分，
判分前清除 agent 对测试目录的任何改动（防作弊）。

### 1.4 SWE-bench 如何判分（为什么是硬证据）

判分用**维护者当年修 bug 时一起提交的官方测试**——agent 全程看不到、改不了。

1. **起点**：仓库 checkout 到 bug 引入的 commit（坏状态），agent 在此基础上改代码。
2. **叠加官方测试**：agent 改完后，判分器把官方 `test_patch`（只含测试、不含修复）
   打上去。这些测试 agent 接触不到。
3. **跑两组测试**：
   - **FAIL_TO_PASS（F2P）**：修复前必失败、修复后必须通过 → 验证"bug 真修好了"。
   - **PASS_TO_PASS（P2P）**：修复前后都应通过 → 验证"没改坏别的"（无回归）。
4. **判定**：**F2P 全过 且 P2P 全过 = RESOLVED（得分）**，否则不得分。二元判定，无部分分。

防作弊/严谨措施：叠加官方测试前清除 agent 对测试目录的改动；P2P 取"修复前确实
能通过"的样本做基线。**对错由第三方隐藏测试客观判定**——这是 SWE-bench 结论可信
的根本。HumanEval+ 同理（用 EvalPlus 强化隐藏测试集判分）。

## 2. 不同难度的省 Token 结果（实测）

> 本章实测用 **Sonnet 4.6 扮演本地 worker**，对应**双卡档（MiniMax-M3 ~76%）**；
> 单卡（Haiku≈Qwen）与四卡（85%）的档位差异见 §4.1–4.4。

### 2.1 总览：每种任务形态的最优方法与省钱幅度

| 任务形态 | 最优架构 | 云端省钱 | 解题率 | 样本 |
|---|---|---|---|---|
| **可验证函数生成**（HumanEval+） | escalate | **−88%** | 31/31（=baseline） | 30 题 |
| **真实仓库 bug 修复**（SWE-bench） | context-engine | **−23%** | 7/11（=baseline） | 11 实例 |

### 2.2 HumanEval+（可验证生成）：escalate −88%

| 架构 | 解题率 | 云端成本 | vs baseline |
|---|---|---|---|
| baseline（纯 Opus） | 31/31 | \$0.1033 | — |
| **escalate** | **31/31** | **\$0.0119** | **−88%** |
| local-first | 30/31 | \$0.1641 | +59%（每题都审查反而更贵） |

- **29/31 题零云端成本**：本地写解+自测通过→不升级，云端一分钱不花。
- 质量无损：自测通过的题，隐藏 EvalPlus 测试也通过——本地自验证可信。

### 2.3 SWE-bench（难任务/诊断密集）：只有 context-engine 为正

| 架构 | 解题率 | 云端成本 | vs baseline |
|---|---|---|---|
| baseline（纯 Opus） | 7/11 | \$3.049 | — |
| **context-engine** | **7/11** | **\$2.338** | **−23%** ✅ |
| hybrid | 10/11 | \$4.256 | +33% ❌ |
| escalate | 11/11 | \$5.49 | +71% ❌ |
| local-first | 8/11 | \$3.124 | −2.5% |
| **oracle（理论最优路由）** | 8/11 | \$1.988 | **−35%** |

- 难任务上**只有 context-engine 省钱且不掉质量**。其它方法要么更贵（hybrid/escalate
  陷入协调循环），要么掉解题率（local-first）。
- **机制验证**：context-engine 把云端**输入侧 −23%、输出侧 −24%**——本地接管探索后
  云端不再反复读代码，且拿到好上下文后推理更聚焦。本地免费承担了 \$3.15 探索量。
- **最难的一题 pylint-7114**：baseline 花 \$0.78 还**失败**；context-engine \$0.25
  **解出来了**——省钱同时提升质量。

### 2.4 为什么 escalate 在难任务上失败（关键教训）

同一套 escalate 代码：HumanEval+ −88%，SWE-bench +71%。唯一区别是**本地能否自证
正确**。SWE-bench 看不到判分测试，本地无法可信地报"已解决"→ 几乎每题都升级。

**但注意：+71% 不是"升级"本身的代价**——本地免费，若云端从干净状态重做，成本应
恰好 = baseline（0%）。实测那次解题率甚至没降（11/11 > baseline 7/11）。**超出的
71% 全部来自"脏交接"**，钱花在云端消化失败现场上：
1. **输入侧变大**：云端 prompt 被塞进本地失败笔记（≤3K 字符）+ 半成品 diff
   （≤15K 字符），且多轮对话每轮都背着它（缓存也要付一次写入）；
2. **脏工作区**：本地改了一半的代码留在仓库里，云端要 diff、判断保留/回滚、回滚后
   重读——都是 baseline 没有的工具轮次；
3. **错误锚定（最贵）**：错误的半成品把云端带偏，先沿本地的错误假设查下去、烧几轮
   才推翻重来（单卡 context-engine +12% 是同一机制：坏包误导云端）。

→ 两个教训：① **省钱的前提是本地能闭环验证正确性**（决定自解率）；② **升级必须
干净交接**（决定地板是否成立）：丢弃半成品、弱本地不带包、强本地只带压缩上下文包。
交接协议一变，同样的分工成本从 0% 飙到 +71%——这正是 Agent 设计的核心变量之一。

## 3. 省 Token 的统一原理

> **省 token = 把"不需要云端顶级智能、但消耗大量 token"的工作，搬到免费的本地。**

不同任务，这块"可外包工作"是不同的东西，所以最优架构随任务形态变：

| 任务形态 | 可外包给本地的大头 | 方法 | 实测省 |
|---|---|---|---|
| 可验证生成 | 整个求解（本地能自证） | escalate | −88% |
| 难 bug 修复 | 代码探索/定位（不需自证，只需会读码） | context-engine | −23% |

> 注：批量多文件生成（云端编排、委派样板代码给本地）的 hybrid 架构，在内部
> 自造任务上观察到约 −26%，但因属"自出题自判分"未列为硬证据；要补成公开硬证据，
> 下一步用 BigCodeBench（公开、调真实库、自带 unittest）。见 §6。

**context-engine 的独特价值**：它**不要求本地能自证正确**，只要求本地会读代码、会
grep——这是端侧小模型也能做好的，所以能用在 escalate 失败的难任务上。这正是
AI station 的核心能力：**本地当云端"免费的眼睛和手"，云端当大脑。**

## 3.5 端侧路由 Agent（产品组件）

端侧资产不只是一个"worker 模型"，还应导出一个**端侧路由 Agent**——它在每个任务
进来时决定"**这题上云还是本地解决**"，并在上云时先做压缩。这是整套方案能否省钱的
中枢，且**必须跑在端侧**：判定逻辑若上云问 Opus，就先花了一笔云端钱，违背初衷。

### 它干两件事

1. **路由判定**：本地先尝试 → 自查/跑测试 → 只在"卡住/超预算"时才升级上云。
2. **上云时当上下文引擎**：决定上云后，不把整个问题甩给云端，而是先把代码探索/
   定位做完、打成压缩包再上云（即 context-engine）。

### 关键实测：判定信号怎么选（决定成败）

我们实测了两种路由信号，结论很硬（数据见 `swebench/RESULTS_CONTEXT_ENGINE.md`）：

| 路由方式 | 信号 | 结果 | 结论 |
|---|---|---|---|
| **事前文本路由** | 本地读 issue 文本 + grep，预判难易 | **+10%**（更贵） | ❌ 11 题全被判"本地能搞定"——**光看题面判不出难度** |
| **事中路由** | 本地先真干，小预算内没通过测试才升级 | 难子集 **−41%** | ✅ 按"实际卡住没"路由才有效 |
| oracle（per-instance 最优上界） | 上帝视角选对每题 | −35% | 证明正确路由的 headroom 真实存在 |

**核心教训**：路由判定要基于"**本地先试、卡住才升级**"的**事中**信号，而不是"读题面
预测难易"的**事前**信号——后者实测失败。

### 一个必须明确的边界

路由 Agent 的可靠度取决于**任务能否本地自验证**：
- **可验证任务**（自带测试/TDD）：本地能客观判"我成了没"→ 路由信号可信 → 可省到 −88%。
- **不可验证任务**（开放式 bug、模糊需求）：本地**无法可信判断自己对没对**（看不到
  隐藏验收标准）→ 这时不该让本地"判定要不要上云"，而应**直接走 context-engine**
  （本地只管探索打包、判定权交给云端）——双卡及以下难任务的稳健路径。
- **例外（回应"难任务不能本地先做完再验证吗"）**：可以，且随本地变强越来越划算——
  难任务里**自带部分裁判的子集**（能写复现脚本 / 有现成相关测试）照样走"先试+高门槛
  自证"：四卡代理实测 **3/11 自解、零假阳性**（恰好都是有现成测试的题）→ escalate
  −29%（85% 设定反推 −40%），反超 context-engine。瓶颈不在"能不能先做"，而在**验证
  信号靠不靠谱**：bug 对应的测试往往本就不存在（否则 CI 早抓住），"现有测试全过"≠修好，
  自写复现只覆盖症状——所以要"高门槛自证 + 失败时把探索笔记打包交给云端"（escalate
  与 context-engine 是同一条流水线的两段）。
- **实验设定偏保守（重要）**：我们的 escalate 用**二元自评**（"不确定就升级"），这会
  **低估**难任务省钱率。真实工作流是：修完 → **跑复现验证** → **验证失败才交付云端**
  ——而真实 bug 通常自带复现路径（报告者见过症状），本地至少能验"症状消了没"（回归
  风险仍在）。SWE-bench 的全隐藏判分是偏保守的设定 → **实测难任务省钱率应视为下限**。
- **交接内容随本地能力分档**：弱本地（单卡）→ **干净现场**（丢弃一切——它的笔记也会
  误导云端，+12% 教训）；强本地（双/四卡）→ **总结问题**交付（bug 是什么、试了什么、
  为何失败、相关代码在哪）——可信的总结省掉云端探索（context-engine −23% 佐证）。
- **时间换 token（两本账分开算）**：本地先试永远增加**时间**成本（本地尝试 + 可能的
  云端重做），但配上分档交接后 **token 成本每一档都 ≤ baseline**。→ 延迟不敏感的负载
  （CI / 批量重构 / 过夜任务）应**全部 local-first**（时间近乎免费）；交互式任务按
  "延迟预算"决定是否直接上云。**延迟敏感度是路由的第三个信号**（前两个：任务可验证性、
  本地-云端差距）。

→ 产品形态：**端侧资产 = 端侧 worker 模型 + 端侧路由/上下文 Agent**。后者默认行为：
可验证任务用"事中路由（本地先试→失败升级）"，不可验证任务用"context-engine
（本地探索打包→云端决策）"。**这个 Agent 才是护城河**：硬件可复制，端云协同的编排
逻辑不易复制。

> **路由地板（为什么绝不亏钱）**：无论走哪条路，**兜底都是纯云端 baseline**——本地
> 免费尝试，一旦判定搞不定，云端**从干净状态**接手（`git checkout` 丢弃本地半成品、
> 不为读它付费），此时云端成本 = baseline，省钱率 = 0%。所以**下限恒为 0（持平）、
> 绝不为负**。要点：升级时**不要把本地的失败产物硬塞给云端消化**（那会让云端多花
> token 去理解/推翻，正是早期裸 escalate 在 SWE-bench +71%、裸 context-engine 单卡
> +12% 的根因）。有了这条地板，"本地做完失败再让云端做"在设计上**至少不亏**。

## 4. 什么情况下盈利（三档真实售价，人民币）

> 售价：单卡 ¥20,000（~$2,778）/ 双卡 ¥40,000（~$5,556）/ 四卡 ¥80,000（~$11,111）。
> 汇率 7.2。云端 API 按 USD 计、本地算力免费，故只看"云端月省钱 vs 机器价"。

### 4.1 盈利公式

省钱率是**百分比**（对 token 绝对价格免疫），机器年价值随之线性放大：

```
年节省(USD) = 云端月消耗(USD) × 12 × 混合省钱率(%)
回本年数    = 机器售价(USD) / 年节省(USD)
```

**关键前提——路由地板：系统绝不亏钱。** 端侧路由 Agent（§3.5，本方案的核心资产）
保证：本地**免费**先试；一旦搞不定，云端**从干净状态接手**（丢弃本地半成品、不为
读它付费）。因此**最坏情况 = baseline = 省 0%（持平），永远不会为负**。任何"反而更贵"
的数字都来自**没有路由地板的裸架构**（把本地的坏产物硬塞给云端消化），是反面教材、
不是产品形态。

**省钱率随档位变化**（更强本地 → 可外包给免费本地的工作越多 → 省得越多）。
SWE-bench 难任务**逐档省钱率**（已应用路由地板）：

| 档位 | 本地模型 | 能力(Verified) | 难任务省钱率（迭代流,估） | 一次性判分口径（方法学下限） |
|---|---|---|---|---|
| 单卡 | Qwen-122B | ~68% | **≈−20%** | 0%（持平；裸 context-engine +12% 为反面教材） |
| 双卡 | M3 | ~76% | **≈−45%** | −23%（context-engine 实测，Sonnet 代理 7/11） |
| 四卡 | GLM-5.2 | **85%（偏保守）** | **≈−65%** | −40%（escalate 反推，自解 ~40%） |

> **逐档解读（迭代流）**：真实工作流里 bug 自带症状复现，本地**免费迭代到复现通过**
> 再交付（烧时间不烧 token），难任务省钱率 ≈ 带裁判的 pass@k 自解率——但**受能力
> 天花板压制**（迭代救不了架构级 bug、裁判不完备致回归返工）：单卡 ≈−20%、
> 双卡 ≈−45%、四卡 ≈−65%（估，待实测）。升级时**干净交接 + 按档位带包**（弱本地
> 干净现场、强本地总结问题），最坏 = baseline 不为负。一次性判分列是保守实验下限
> （§4.4b），不作为产品口径。

可验证负载（TDD/测试生成）省钱率随能力一路爬（单卡 −63% → 双卡 −88% → 四卡 −95%，
见 §4.3a）。

### 4.2 完成度（本地自解率）反推：从能力推省钱率

省钱率由**本地完成度（self-solve 率，自解的题零云端成本）**驱动。用两组实测点反推
四卡（设为 85% 能力）的完成度：

| 档位 | 能力(Verified) | 容易任务完成度 | 难任务完成度 | 依据 |
|---|---|---|---|---|
| 单卡 | ~68% | **83%** | **~0%** | 实测（HumanEval+ 25/30 自解；难任务几乎全升级） |
| 双卡 | ~76% | **94%** | **~9%** | 实测（HumanEval+ 29/31 自解；SWE-bench ≈1/11 自解） |
| 四卡 | **85%** | **~98%** | **~40%** | **反推外推**（易：83→94→饱和近 100；难：76%→9%、81%→27% 实测，外推 85%→~40%） |

**从完成度到省钱率**：
- 容易/可验证任务（escalate）：`省钱率 ≈ 1 − 2×(1 − 完成度)`（系数 2 = 升级出去的多为
  最难题、单题云端成本 ~2× 均值；实测拟合 83%→−63%、94%→−88% 均吻合）→ 四卡 98%→**−95%**。
- 难任务：`省钱率 ≈ 难任务完成度`（自解者零云端、升级者从干净态≈baseline）。上表
  难任务完成度是**一次性 pass@1 锚点**；迭代流下完成度 ≈ 带裁判的 pass@k（显著更高）
  → 困难任务估 ~20%/45%/65% → ≈−20%/−45%/−65%；简单任务迭代自解率 ~90%/96%/98% →
  −80%/−92%/−96%（实测硬底 −63%/−88% 为合同级）。下限恒为 0%（干净升级），不为负。

**口径：真实迭代工作流**（bug 自带复现、本地免费迭代；困难列 = 带裁判的 pass@k

| 本地≈云端（前沿 int4，差半步） | →−100%(置信盲发) | — | — | →趋近 −100% |

### 4.4b 方法学注：一次性判分的保守实验（下限，不作为产品口径）

我们的对照实验刻意用**三重保守设定**（一次性隐藏判分 + 本地 20 轮上限 + 二元自评
"不确定就升级"）以获得无可辩驳的硬证据。该口径下难任务列仅：单卡 0%（持平）、
双卡 −23%（实测）、四卡 −40%（反推），混合 −50%/−75%/−84%，2 年门槛 $230/$309/$551。
**这不是真实工作流**：真实 bug 自带症状复现、本地可免费迭代（§1.1），主表因此采用
迭代流口径（难任务列 = 带裁判的 pass@k 自解率估计，打了无复现任务与回归风险两个
折扣）。**下一步实验**（§6）：放开迭代预算重跑 SWE-bench，把迭代流列变成实测。

**两条结构规律**：
1. **难任务列的渐近线是 −100%，靠"置信盲发"够到（第六种模式）**：最差 0%（本地帮
   不上走纯云端）；往上 context-engine 封顶 ~−30%（双卡 −23%）；四卡改 escalate →
   −40%（自证子集自解）。\***本地≈云端时**：盲发 = baseline 质量（同一个模型、得分
   相同）——我们的 baseline 运行本身就是这个数据点（Opus 4.8 独解 7/11、$3.05；跑在
   本地即同样 7/11、云端 $0 = −100%）。此时最优模式是**置信盲发**：本地对有把握的题
   直接交付（不必跑测试自证，判断力≈云端，云端复核不增加信息）、没把握才升级。
   **统一公式：云端的边际价值 = 能力差距 × 定位差距的能力**；差距→0 时价值→0、省钱
   →−100%。"零质量容差 + 必须自证"策略的上限（~−50/60%，可自证比例）不是架构上限——
   接受与差距相当的质量容差即可继续爬。最优模式随差距连续过渡：
   纯云端(0%) → context-engine(−23%) → escalate(−40%) → 置信盲发(→−100%) → 纯本地。
2. **简单列随能力一路爬、可趋近 −100%**：本地整题自解 + 自跑测试，省钱率 ∝ 本地
   自解率 → **单卡 −63%(实测) → 双卡 −88%(实测) → 四卡 ~−95%(反推) → 本地=云端趋近 −100%**。
   **关键**：可验证任务上**连最弱的单卡都省 63%**，因为弱模型也能跑测试自证（但会留
   少量假阳性，随本地变强而收窄：单卡 2/30 → 双卡 0 → 四卡可忽略）。

→ 省钱两杠杆：**①负载往可验证移（沿行右移，最强杠杆）②本地模型升级（整行下移）**。
两列都随能力上涨；可验证列爬得更快、无封顶；难任务列上限卡在「可自证比例」、随本地
变强从 context-engine 解封到 escalate。

**以四卡 GLM-5.2（85% 能力，¥80k≈$11,111）为例，按负载类型的回本**：

| 负载类型 | 省钱率 | 2年回本需月消耗 | $1000/mo | $2000/mo | 来源 |
|---|---|---|---|---|---|
| 困难(仓库级 bug) | ≈−65% | ≥$712/月 | 1.4年 | 0.7年 | 迭代流估 |
| 中等 | ≈−80% | ≥$579/月 | 1.2年 | 0.6年 | 插值 |
| 较易 | ≈−90% | ≥$514/月 | 1.0年 | 0.5年 | 插值 |
| 简单(函数级·TDD) | ≈−96% | ≥$482/月 | 1.0年 | 0.5年 | 迭代流估 |

→ 迭代流口径下四卡全负载 $600/月内 2 年回本；"引导可验证"的价值从"省钱生死线"变为
"**降风险**"（可验证列是实测硬底、假阳性可忽略，难任务列仍是待实测的估计）。

### 4.5 核心判断（价格随档位翻倍 + 能力门槛）

- **单卡 ¥20k**：简单任务迭代估 −80%（实测硬底 −63%）+ 困难 ≈−20% → 混合 ≈−68%，
  $170/月即 2 年回本。定位：**预算型个人**，可验证工作流（TDD）是实测保底卖点。
- **双卡 ¥40k**：简单任务迭代估 −92%（实测硬底 −88%，零假阳性）+ 困难 ≈−45% →
  混合 ≈−83%，$280/月即 2 年回本。小团队 / 顶级个人。
- **四卡 ¥80k（85% 能力，偏保守）**：**团队/CI 共享设备**，混合 ≈−90%、$516/月即
  2 年回本；4 人共享（$600/月）1.7 年。**绝不单人卖**（单人回本慢于低档，价值在共享与更强本地）。

**两条铁律**：① 最坏 = 干净升级回 baseline（0%），**任何档位不亏钱**；② **省钱率升幅
抵不过价格翻倍** → 高档位靠**团队摊薄**回本，不是单人更快。

### 4.6 两个放大器

1. **把负载引导到可验证工作流**（TDD/测试生成/批量重构）：沿难度轴左移负载（四卡困难 ≈−65% → 简单 ≈−96%），
   且简单列有实测硬底（−63%/−88%）背书、假阳性可忽略。
2. **云端涨价对冲**：省钱率是百分比 → 机器价值随云端 token 单价线性放大；云端涨 2x，
   所有档位回本期减半。机器本质是"做空云端涨价"的对冲。

### 4.7 一个必须正面回答的问题：云端还是要订阅，省钱怎么兑现？

**对——云端依赖去不掉**（前沿判断力买不断，只能持续付费），端云结合是"少付"而非
"不付"。省下的 token 兑现成钱的方式，取决于客户的云端**计费模式**：

**① API 按量计费（团队 / CI / agent 重度用户的主流）**
省 token = 省美元，一一对应。本报告全部回本表（$5/$25 per Mtok）就是为这类客户算的，
结论直接成立。**这是"省钱"故事的主攻市场。**

**② 包月订阅（个人 Pro/Max 类）——省了 token，账单不会自动变少**，要换三种方式兑现：

| 兑现方式 | 机制 | 量级示例 |
|---|---|---|
| **降档** | 订阅本质是限额（周配额/时窗），省 token = 同档能干 5–20 倍的活 | Max $200/月 → Pro $20/月 |
| **减座位** | 机器扛走 ~80% 负载后，团队所需座位数下降 | 10 座 → 3 座 |
| **不撞限额** | 重度用户最痛的是被限流卡住，机器吸收大头 = 免升档 | "免升档"价值 |

→ 订阅制下省钱率的兑现**打折但不归零**：货币从"$/token"变成"档位 × 座位数"。

**③ 诚实的风险：token 补贴期**。当前大模型公司普遍补贴，订阅折算的有效 token 单价
远低于 API 牌价——云端越便宜，省 token 的美元价值越缩水、回本越慢。三个对冲：
1. **涨价期权**（§4.6）：补贴不可持续，云端涨价时机器价值线性放大；
2. **主攻 API 计费客户**：他们省的是真金白银；
3. **不依赖计费模式的第二条腿——隐私/合规**：context-engine 的机制本身就是"整个
   仓库不上云、云端只看到压缩上下文包"。**省 token 的机制 = 缩小数据暴露面的机制**，
   对合规敏感客户这条价值与订阅与否无关。

**④ 产品设计空间**：
- **机器捆绑云端 credits** 做一体化订阅（一笔账单 = 机器分期 + 云端代理），消掉
  "两笔钱"的心理账户问题，赚云端转售差价。
- **与云厂商联合推「端云协同版 coding plan」**：机器当入场券，云端只接升级上来的题
  （量少且都是真难题）→ 订阅可以定一个**更低的价档**。对云厂商同样有利：①获客
  （买机器的都是重度用户）②算力减压（~80% 的 token 被端侧消化）③留存（用户被
  端云工作流锁定）。这把"还要订阅"从劣势翻成双赢的渠道合作。

## 5. 商业建议（三档真实售价下）

1. **单卡 ¥20k**：按"**可验证工作流（TDD）省钱盒子 + 私有化**"卖给预算型个人——
   简单任务实测硬底 −63%（合同级）、迭代估 −80%；困难任务 ≈−20%（估）不作硬承诺。
2. **双卡 ¥40k**：混合 ≈−83%、$280/月即 2 年回本，卖"团队头部开发者专机/小团队"。
3. **四卡 ¥80k = 团队/CI 设备（设为 85% 能力）**，混合 $516/月即 2 年回本、
   4 人共享 1.7 年，按"团队共享 + 负载左移"卖。**不单人卖。**
4. **所有档位的共同放大器**：把负载引导到可验证工作流（从估计列移进实测硬底列、
   消掉假阳性）+ 隐私合规私有化卖点（与价格无关的硬价值）。
5. **对外承诺分两层**：实测硬底（可验证 −63%/−88%）写进合同；迭代流估计
   （困难 ≈−20%~−65%、简单迭代 −80%~−96%）作为案例/上行空间讲，待 §6 实验转正。
6. **按计费模式分开讲故事**（§4.7）：API 客户讲"回本表"（省真钱）；订阅客户讲
   "降档 / 减座位 / 不撞限额 / 代码不出域"；进阶产品是"机器 + 云端 credits"一体化订阅。

## 6. 局限与下一步

- **样本与方差**：SWE-bench 每实例单次运行，agent 成本方差 ±50%；−23% 是 11 题合计，
  方向稳健但精确值需每题 3 重复取均值。
- **本地模型代理**：用 Haiku 4.5（Verified 73.3%）扮演端侧模型，与单卡档真实模型
  Qwen3.5-122B-A10B（~72%）几乎同分——故单卡档省钱率已被实测覆盖，非估计；
  双卡/四卡模型更强，省钱率只会更高（见 §0.1）。
- **计费模式风险**（§4.7）：回本表按 API 牌价计；订阅制客户的兑现要折算成
  "降档/减座位"，且 token 补贴期省下的美元缩水——对冲是涨价期权 + 隐私/合规
  这条不依赖计费的腿。
- **三重保守设定低估难任务省钱率**（§1.1 修正、§3.5）：①一次性隐藏判分（真实 bug
  可免费迭代：修→验→再修，烧时间不烧 token，错了还有外层反馈兜底）②本地 20 轮上限
  ③二元自评（"不确定就升级"）→ 实测难任务列是**下限**。待改进：放开本地迭代预算
  重测（预期难任务列向可验证列收敛）+ 置信分级自评 + 分档交接协议。
- **下一步**：
  1. **补 BigCodeBench**（公开、调真实库、自带 unittest）：把"批量多文件生成"这个
     任务形态也变成公开硬证据，替掉已弃用的自造 calclang。
  2. **in-flight 路由**：云端小预算内自探索，卡住才注入免费本地包（初步难子集 −41%，
     待调预算/成功检测）→ 逼近 oracle 的 −35%。
  3. **真实 vLLM 端点**：把 worker 换成本地实跑的端侧模型（单卡 Qwen3.5-122B /
     双卡 MiniMax-M3 / 四卡 GLM-5.2），按档位得到产品级真实数字，替掉 Haiku 代理。
  4. **统计化**：全量 SWE-bench + 每题 3 重复，给出带置信区间的省钱率。
